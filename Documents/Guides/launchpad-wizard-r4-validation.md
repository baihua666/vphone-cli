## 创建验收阻塞：原 Core 克隆崩溃

释放临时发布分片及旧的可再生成构建缓存后，系统报告可用容量 65,668,259,840 字节，超过 61 GiB 的导入预检要求。点击同一「创建并启动新虚拟机」按钮后，镜像校验与原 CLI 导入完成，但 `vm clone ... --new-identity` 异常退出；向导显示「失败，可重试」。业务模块清理了本次暂存目录，目标 `wizard-r4-check-20261026` 未生成，没有启动或半成品实例。

崩溃证据：2026-10-26 12:22（北京时间），`EXC_BREAKPOINT / SIGTRAP`，调用栈为 `VPhoneBundleActivity.processesHolding` → `requireStopped` → `VPhoneBundleOperations.clone`。现场原包的反汇编确认：取得 `proc_pidfdinfo` 的设备编号后，最高位为 1 时进入 Swift 整数转换陷阱。对应源码为 `VPhoneKit/VPhoneCoreKit/Bundle/VPhoneBundleActivity.swift` 的 `dev_t(st.vst_dev)`。

本机 `/dev/null` 设备编号是 `2910354059`，超过有符号 32 位上限。只读宿主探针发现 523 个可检查进程持有这类设备文件，包括 CLI 自己；因此只修改 Launchpad 子进程的标准输入不能解决全进程扫描问题。此问题不涉及镜像内容或内存容量，也不能用多重试几次、跳过停止检查或直接改写设备身份代替修复。

遵守“不改 Core”的约束，本轮未修改底层。若后续获用户单独确认，最小修复候选是按位保留设备编号的转换及边界测试；仍须构建新 Core、核验签名身份并单独验收，不能把原包替换成同名文件或自动改绑业务实例。**创建启动与导入后启动失败重试尚未通过，r4 不作为已验收正式版发布。**
